# План: фоновый индекс внешних источников + курсорная пагинация

Статус: **не реализовано, план для следующей итерации**. Отделено от текущего кода намеренно —
описывает архитектурный шаг, который требует новой инфраструктуры (миграция, cron), а не
точечное исправление.

Контекст: [README.md](./README.md) (текущая реализация внешнего поиска), спека
`Global_AI_Vessel_Search_Prompt.md` (§7, §9, §10, §25). Раздел README «Что реализовано и что нет»
уже называет это следующим шагом — этот файл его расписывает.

## Проблема, которую это решает

Сейчас `brilionsProvider` (`providers/brilions/provider.ts`) — это **live-краулинг внутри HTTP-
запроса пользователя**: сайтмап → фильтр по городу → фетч HTML (кэш 24ч) → детерминированное
извлечение → AI-извлечение удобств (Anthropic, не персистентно кэшируется) → нормализация →
фильтр по критериям.

Тактическое исправление (уже сделано, см. git-историю) убрало жёсткий предел «10 карточек»,
заменив его на тайм-бюджет (`context.timeoutMs`) с ограниченным параллелизмом и in-memory кэшем
AI-извлечения. Это подняло практический потолок (наблюдалось 60 карточек за ~18с на холодном кэше
вместо жёстких 10), но принципиально не решает проблему:

- Число карточек по-прежнему зависит от того, сколько успели зафетчить за тайм-бюджет, а не от
  того, сколько реально подходящих судов есть на сайте (~312 судов в каталоге).
- In-memory кэш AI-извлечения не переживает холодный старт/рестарт/деплой и не расшарен между
  инстансами функции (Vercel Fluid Compute переиспользует инстансы, но не гарантирует один и тот
  же для всех запросов).
- Постраничная выдача **поверх этой модели не работает**: «страница 2» результатов означает либо
  повторный live-фетч сайта (медленно, если не закэшировано), либо необходимость заранее пройти
  весь каталог — то есть тот же объём работы, просто отложенный на клик «ещё».
- CLAUDE.md §9 требует курсорную пагинацию для масштабируемости — сейчас её нет ни у внутреннего
  (`INTERNAL_CANDIDATE_LIMIT = 40`, просто обрезка), ни у внешнего поиска.

## Целевая архитектура

```
Сейчас:  запрос → live-краулинг сайта (bounded by time) → нормализация → выдача
Целевое: cron → полный обход каталога → индекс (БД)
         запрос → SELECT по индексу (как internal-provider.ts) → выдача, курсорная пагинация
```

Поиск пользователя перестаёт ходить в сеть вообще. Это делает внешний источник той же природы,
что и `internal-provider.ts`: быстрый, дешёвый, предсказуемый SELECT с фильтрами.

## Шаг 2a — индексная таблица + фоновый обход

### Миграция: новая таблица `external_vessels`

Отдельная от `search_page_cache` (которая остаётся как есть — кэш сырого HTML для вежливости
краулинга и аудита, не для обслуживания поиска). Новая таблица хранит **структурированный**
результат нормализации, одну строку на судно на источник:

```sql
create table public.external_vessels (
  id uuid primary key default gen_random_uuid(),
  source_domain text not null references public.search_sources (domain),
  external_id text not null,           -- entry.slug у brilions
  url text not null,
  url_en text,
  city_slug_guess text,                -- для фильтра по городу без похода в JSON

  -- поля VesselSearchResult в столбцах, а не jsonb — чтобы фильтровать в SQL,
  -- как внутренний поиск, а не в JS после загрузки всего
  name text,
  vessel_type text,
  vessel_type_raw text,
  manufacturer text,
  model text,
  year integer,
  length_meters numeric,
  guests integer,
  cabins integer,
  country text,
  city text,

  -- остальное, что не участвует в WHERE-фильтрах, можно оставить jsonb
  extracted jsonb not null,            -- полный нормализованный VesselSearchResult
  content_hash text not null,          -- content_hash страницы на момент извлечения

  first_seen_at timestamptz not null default now(),
  last_seen_at timestamptz not null default now(),   -- обновляется каждым успешным обходом
  updated_at timestamptz not null default now(),

  unique (source_domain, external_id)
);

create index external_vessels_city_idx on public.external_vessels (city_slug_guess);
create index external_vessels_type_idx on public.external_vessels (vessel_type);
create index external_vessels_last_seen_idx on public.external_vessels (last_seen_at);
```

`last_seen_at` — механизм «пропал с сайта»: если обход прошёл, а строку не тронул, значит судно
больше не в сайтмапе или страница перестала извлекаться. Стратегия: не удалять сразу (страница
могла быть временно недоступна), а исключать из выдачи строки с `last_seen_at` старше N обходов
(например, 3 подряд), удалять — отдельным, более редким job'ом.

RLS: как у `search_page_cache`/`search_sources` — только `service_role`, никакой клиентский
доступ (данные читает только сервер через `internal-provider.ts`-подобный слой).

### Фоновый обход

Vercel Cron → API route (например `POST /api/cron/reindex/brilions`, защищённый секретом cron'а,
не публичный) → переиспользует существующую инфраструку без изменений:

- `sitemap.ts` — тот же парсинг.
- `crawl/safe-fetch.ts`, `crawl/robots.ts`, `crawl/cached-fetch.ts` — та же SSRF-защита и HTML-кэш
  (не выкидывать, полезен для повторных прогонов и отладки).
- `extract.ts`, `ai-extract.ts`, `normalize.ts` — тот же pipeline извлечения.
- Разница с текущим `provider.ts`: обходит **весь** сайтмап (не режет по времени пользовательского
  запроса), пишет каждый результат в `external_vessels` через upsert on `(source_domain,
  external_id)`, обновляя `last_seen_at`.
- AI-извлечение удобств кэшируется **персистентно** по `content_hash` (страница не изменилась →
  не гонять Anthropic заново) — сюда естественно переезжает `amenitiesCache` из тактического
  решения, просто в БД вместо `Map` в памяти процесса. Это то самое `ExtractionCache`, которое
  README уже называет нереализованным пробелом.

Расписание: раз в 12–24ч (комментарий `SITEMAP_CACHE_MS` в текущем коде уже фиксирует допущение
«каталог меняется по неделям, не по минутам»). Обход всего каталога (312 страниц) с той же
параллельностью, что и тактическое решение (`FETCH_CONCURRENCY`), без тайм-бюджета
пользовательского запроса — может занимать минуты, это нормально для фонового job'а.

### Переключение `brilionsProvider`

`runSearch` меняется с live-краулинга на:

```ts
supabase
  .from("external_vessels")
  .select(...)
  .eq("source_domain", "brilions.com")
  .in("city_slug_guess", [...matchedSlugs])   // или без фильтра, если matchedSlugs = все города
  .gte("last_seen_at", staleness_cutoff)
  // + vessel_type / guests фильтры, как во internal-provider.ts
```

Тот же контракт `ExternalSearchProvider` (`providers.ts`) — оркестратор (`global-search-service.ts`)
не меняется вообще, это и есть весь смысл того, что интерфейс существует.

**Переходный период**: имеет смысл держать live-краулинг провайдер какое-то время рядом (например
под другим `id`, не подключённым в `page.tsx`) как ручной инструмент проверки — сравнить, что
индекс не разошёлся с реальным сайтом, прежде чем полностью полагаться на cron.

## Шаг 2b — курсорная пагинация

CLAUDE.md §9: «пагинация курсорная» — обязательное нефункциональное требование, не только для
внешнего поиска. Затрагивает и `internal-provider.ts` (`INTERNAL_CANDIDATE_LIMIT = 40` — сейчас
просто обрезка без возможности допрокрутить).

### Где встраивается в конвейер

Пагинация — **после** ранжирования и дедупликации (`global-search-service.ts`: `dedupeResults` →
`rankResults`), не до. Дедупликация должна видеть весь объединённый набор кандидатов сразу — иначе
одно и то же судно, найденное во внутренней базе и во внешнем индексе, может попасть на разные
страницы результата и не схлопнуться (`dedupe.ts`'s `dedupeResults` работает на всём массиве).

### Форма курсора

Непрозрачный токен (base64 JSON), кодирующий последнюю позицию отданной страницы — не номер
страницы (offset дрейфует при вставках/обновлениях между запросами, CLAUDE.md явно требует курсор,
не offset):

```ts
interface SearchCursor {
  score: number;   // ranking.score последнего элемента предыдущей страницы
  id: string;      // tie-break при равном score
}
```

Сортировка результатов: `(ranking.score DESC, id ASC)` — тот же порядок, что уже использует
`rankResults`, плюс детерминированный tie-break. Курсор непрозрачен для клиента (кодирует
внутренний порядок, не подразумевает контракт формата).

### Изменения в коде

- `global-search-service.ts`: `runGlobalVesselSearch` принимает `cursor?: string, pageSize?: number`
  (в `GlobalSearchOptions`), возвращает `results` только для текущей страницы + `nextCursor: string
  | null` в `UnifiedSearchResponse`.
- `internal-provider.ts`: `INTERNAL_CANDIDATE_LIMIT` перестаёт быть жёсткой обрезкой результата —
  либо тянет достаточно кандидатов, чтобы прокрутить N страниц вперёд, либо (проще для первой
  версии) полностью материализует отранжированный список один раз за поисковый запрос и просто
  режет на странице `pageSize` — сам DB-запрос всё ещё ограничен разумным потолком (например 200),
  чтобы не тянуть всю таблицу целиком.
- UI (`discover/page.tsx`, `result-card.tsx` не меняется): кнопка «Показать ещё» —
  Server Action, дергающий `runGlobalVesselSearch` с сохранённым `interpretedCriteria` +
  новым `cursor`, дописывающий карточки к уже отрендеренному списку. Это требует клиентского
  компонента-обёртки вокруг списка результатов (сейчас список рендерится полностью на сервере в
  `page.tsx`) — открытый вопрос дизайна, см. ниже.

## Открытые вопросы, которые нужно решить перед стартом

1. **Платформа cron'а**: Vercel Cron (`vercel.ts` → `crons`) — самый нативный вариант при
   деплое на Vercel, не требует новой инфраструктуры. Альтернатива — Supabase scheduled function,
   если захочется держать логику обхода ближе к БД. Рекомендация: Vercel Cron, раз проект уже на
   Vercel.
2. **Судьба `search_page_cache`**: оставить как есть (кэш сырого HTML, полезен для повторных
   прогонов индексатора и отладки) или свернуть в `external_vessels.extracted`/`content_hash` и
   отказаться от отдельного хранения HTML. Рекомендация: оставить раздельно — HTML полезен для
   диагностики, когда извлечение вдруг перестаёт находить поле (как уже было с AI-селектором,
   см. README «Что проверено вживую», пункт 3).
3. **Политика удаления пропавших судов**: сколько подряд непопаданий в обход считать «действительно
   пропало» и когда физически удалять строку из `external_vessels` (сейчас предложено: 3 обхода
   до вывода из выдачи, отдельный более редкий job до физического удаления). Нужно решить порог.
4. **UI для «Показать ещё»**: клиентский компонент с Server Action или client-side fetch к route
   handler — сейчас список рендерится полностью на сервере, добавление пагинации меняет эту
   границу. Нужно решить: infinite scroll (`IntersectionObserver`) или явная кнопка — дизайн-
   система (CLAUDE.md §5) склоняется к премиальному travel-журналу, где на мобильных уже
   предполагается карусель — infinite scroll вероятно уместнее явной кнопки, но это решение UX,
   не техническое.
5. **Расширение на будущие источники**: если появится второй внешний провайдер (не только
   brilions), `external_vessels.source_domain` уже спроектирован под это — но `city_slug_guess`
   специфичен для brilions'овской эвристики slug'ов; для источника без такой эвристики понадобится
   свой способ пре-фильтрации по локации до полного extract. Не блокирует эту итерацию, но стоит
   держать в голове при проектировании столбцов.

## Порядок реализации (рекомендуемый)

1. Миграция `external_vessels` + RLS + индексы. Перегенерировать `database.types.ts`.
2. Cron route + переиспользование `sitemap.ts`/`extract.ts`/`ai-extract.ts`/`normalize.ts` для
   полного обхода, upsert в индекс. Ручной прогон и сверка с текущим live-поиском (переходный
   период из §2a) на нескольких городах.
3. Переключить `brilionsProvider.search()` на SELECT по индексу. Оставить live-провайдер как
   отдельный, не подключённый в `page.tsx` инструмент для ручной сверки ещё на какое-то время.
4. Курсорная пагинация: сначала `global-search-service.ts` + `internal-provider.ts` (только внутренний
   поиск, самая простая проверка контракта), затем расширить на объединённый internal+external
   список, затем UI («Показать ещё»/infinite scroll).

Каждый пункт — рабочее приложение на выходе, по духу CLAUDE.md §10 («не начинай следующий этап,
пока предыдущий не собирается и не проходит тесты»).
